\subsection*{Overall Assessment}
The manuscript is unusually candid: nearly every quantitative claim carries
an explicit scope qualification, and the paper's own Appendix
(Section~A, ``Matched-PSNR/Effective-MSE Comparison'') already runs a
descriptive fairness check of the kind the original reviewers demanded. That
candor is a strength. But reading the manuscript fresh, as a new reviewer,
surfaces two issues that the manuscript states too strongly without the
statistical apparatus to support the claim, plus one process gap that this
fresh-review pass ran into directly. None of these are blocking in the sense
of requiring a new method, but the first two require real exports or a clear
scope limitation before they can be closed.

\subsection*{Finding F1 (Major): the matched-PSNR null result is asserted, not tested}
\label{sec:f1}
Appendix Table~\texttt{tab:matched\_psnr} and the surrounding text now avoid
the stronger phrase ``statistically indistinguishable'' and instead report
identical displayed Top-1 point estimates for six sigma-tunable variants
(\texttt{full}, \texttt{no\_temporal}, \texttt{no\_ncp}, \texttt{unary\_only},
\texttt{no\_dcrf}, \texttt{global\_noise}) at the three targets. This is an
appropriate descriptive correction, but it is not a statistical test of
equivalence. The underlying sample is only 12 paired locations $\times$ 3
seeds $=$ 36 paired binary retrieval outcomes per cell, restricted to one
backbone (ResNet18) and one gallery size (48). This matters because this
comparison is the load-bearing evidence for the paper's central
repositioning: that PPEDCRF's contribution is better quality at matched
privacy rather than more privacy at matched quality. A claim that important
should rest on a real paired test and an explicit statement of how much power
that test had at this sample size, not on rounding alone.

\textbf{Required action.} Use the newly added
\texttt{src/scripts/significance\_test\_matched\_psnr.py} (paired McNemar
exact test plus a query-level cluster bootstrap CI on the Top-1 difference,
run against the same sigma-sweep \texttt{per\_query.csv} exports that already
back Table~\texttt{tab:matched\_psnr}) to report, for each matched-PSNR
target and each sigma-tunable variant compared against \texttt{global\_noise}:
the exact McNemar $p$-value, the bootstrap 95\% CI on the Top-1 difference,
and the minimum discordant-pair asymmetry that would have reached
significance at $\alpha=0.05$ given the realized 36-pair sample (this last
number tells the reader directly how much power the comparison had, rather
than leaving ``statistically indistinguishable'' to be taken on faith).
Integrate the resulting numbers into Appendix~A and soften the main-text
sentence in Section~4.4 (``Fixed-Budget Privacy--Utility and Attacker
Sensitivity'') and the Conclusion accordingly, e.g. from ``statistically
indistinguishable'' to ``no significant Top-1 difference was detected by an
exact paired test ($p>\ldots$), though the 36-pair sample only has power to
detect an asymmetry of roughly 1 in 6 discordant queries.'' If time or GPU
access permits, extending the sigma sweep to at least one more
backbone/gallery cell would materially strengthen this specific claim, but
is not required to satisfy this finding: reporting the real test statistics
on the existing single-cell data is the minimum bar.

\textbf{Completion gate.} A regenerated \texttt{matched\_psnr\_significance.csv}
exists with McNemar $p$-values and bootstrap CIs for every
(\texttt{target\_psnr}, variant) pair currently in Table~\texttt{tab:matched\_psnr}
and is written back into the appendix table or its surrounding text; the
main-text and Conclusion wording is updated to match the tested claim rather
than the rounded point estimate.

\subsection*{Finding F2 (Moderate): the current pipeline's own run-to-run determinism is unverified}
\label{sec:f2}
Appendix Section~``MixVPR Margin Diagnosis and Mitigation Status'' reports
that the current proxy50 run no longer reproduces an adverse MixVPR transfer
result the reviewers cited, and states plainly that no preserved copy of the
earlier run exists to identify why. That is an honest account of a run that
already happened, but it leaves a more basic and directly answerable question
unaddressed: is the \emph{current} code, given its fixed seeds
$\{1234,1235,1236\}$ and current checkpoint, even deterministic from one
execution to the next? If it is, the earlier discrepancy is confidently
attributable to a prior code or checkpoint change rather than to
non-reproducibility of the present numbers, which is a materially stronger
statement to be able to make about every other result in the paper. If it is
not, that is itself an important, currently undocumented limitation that
would affect the credibility of every seed-averaged table in the manuscript,
not just the MixVPR cell.

\textbf{Required action.} Use the newly added
\texttt{src/scripts/check\_run\_determinism.py} to re-run the same benchmark
invocation twice, unmodified, on the same machine and checkpoint (the MixVPR
proxy50 cell is the minimum required scope; the full proxy12/proxy50 export
is preferable if GPU time allows), and diff the two \texttt{per\_query.csv}
or \texttt{summary.csv} outputs. Report the outcome as one sentence in the
appendix MixVPR subsection: either ``re-running the current pipeline twice
under identical seeds reproduces every reported value exactly, so the
discrepancy with the earlier reviewer-cited run reflects a prior code or
checkpoint change rather than run-to-run nondeterminism,'' or, if a mismatch
is found, a description of which fields differ and a follow-up investigation
into the nondeterministic source (candidate causes to check first: unseeded
RNG calls inside a specific backbone loader, non-deterministic cuDNN
algorithm selection, or thread-order-dependent floating-point reduction).

\textbf{Completion gate.} A determinism-check run (real GPU execution,
not a schema smoke test) has produced two independent output directories for
at least the MixVPR proxy50 cell, \texttt{check\_run\_determinism.py} has been
run against them, and its outcome (pass or a named mismatch) is stated in the
appendix.

\subsection*{Finding F3 (Editorial, no experiment required): paper-facing CSVs are not provenance-checked across machines}
\label{sec:f3}
This review pass discovered, while trying to verify the two findings above
against the manuscript's backing data, that \texttt{src/outputs/} is
git-ignored and none of the large \texttt{tomm\_review\_*} run directories
that back the current paper tables exist in this session's working
environment, which is a different machine from the one(s) on which those runs
were executed. This is not a defect in the manuscript, but it is a real gap
in the revision process: there is currently no lightweight, versioned record
of exactly which run (by checksum) produced each paper-facing number, so a
future session on a different machine cannot verify that a table is still
backed by the run it claims without re-obtaining the full multi-gigabyte
output tree.

\textbf{Required action.} Add a short provenance table to
\texttt{docs/experiment\_progress.tex} (or a new
\texttt{docs/experiment\_provenance.md}) recording, for every CSV or JSON
export currently cited by a paper table (proxy12, proxy50, the E1 MSLS
manifests, the E2 sigma-sweep directories, the E4 utility manifests, the E5
KITTI-360 diagnostic), its output path, the code revision (git commit SHA)
that produced it, and a SHA-256 checksum of the file. This is a documentation
task, not a new experiment, and can be completed on whichever machine
currently holds each output tree.

\textbf{Completion gate.} The provenance table exists and lists a checksum
for every export currently cited by a table or figure in \texttt{paper/}.

\subsection*{Priority Order for This Cycle}
\begin{enumerate}
    \item F1 (matched-PSNR significance test) --- highest priority, because
    it is the direct evidentiary basis for the paper's central repositioned
    claim.
    \item F2 (determinism check) --- second priority, because a negative
    result would have paper-wide implications, though the current text is
    not making a false claim, only an unverified one.
    \item F3 (provenance checksums) --- lowest priority, a process
    improvement rather than a manuscript defect, but cheap to complete and
    valuable given this session's own experience.
\end{enumerate}

Both F1 and F2 require execution on a machine with the real monitoring
corpus, the \texttt{sensnet\_final.pt} checkpoint, and a CUDA-capable GPU;
neither the significance test nor the determinism checker itself needs a
GPU (both are pure post-processing over existing or freshly-collected CSV
exports), but the underlying sigma-sweep and MixVPR reruns that feed them do.
The two analysis scripts have been written and schema-smoke-tested against
synthetic data in this session; they are ready to run against real exports
as soon as they are available on such a machine.
